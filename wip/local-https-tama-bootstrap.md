# Local HTTPS Tama Bootstrap Provider Support

Status: proposed on `feature/local-https-bootstrap`

## Summary

Prepare Memovee to run as the host-native OAuth provider behind the Caddy
service generated by Tama Kit. The public issuer becomes
`https://app.localhost`, while Phoenix continues serving plain HTTP on a
private upstream address for Caddy. Memovee remains a normal
`MIX_ENV=dev` process; only the containerized official Tama release runs with
`MIX_ENV=prod`.

This is application-owned work. Tama Kit owns generated topology and proxy
artifacts, but it must not guess or rewrite Memovee's listener, external URL,
trusted-proxy, OAuth, or environment-loader behavior.

## Current evidence

- `Memovee.OAuth.Tama.MCP.Configuration` already loads explicit generated
  values in `dev`, `test`, and `prod` and marks only `dev` and `test` as
  eligible for loopback HTTP.
- `Memovee.OAuth.Tama.MCP` already accepts HTTPS issuer, resource, and Tama JWKS
  URIs without a local-development exception. Production tests cover this.
- OAuth metadata and endpoint URLs derive from the configured explicit issuer,
  so `host.docker.internal` does not need to become a public identity.
- `config/dev.exs` currently binds the Phoenix endpoint to `127.0.0.1`.
  A Caddy container on Linux cannot reach that listener through
  `host.docker.internal`.
- `config/runtime.exs` loads the MCP App Configuration in every environment,
  so generated HTTPS OAuth values already reach `MIX_ENV=dev`.
- External HTTPS URL, broad listener, and trusted-proxy parsing currently live
  only inside the `config_env() == :prod` block. They are not active when
  Memovee runs in development.
- `config/dev.exs` also sets `check_origin: false`; the managed proxy mode
  needs an explicit external WebSocket origin without changing ordinary
  standalone development.
- `.envrc` still looks for `./.memovee.integration.env`; current Tama Kit owns
  the generated provider fragment below `tama/`.
- The application-owned provider contract was removed from `develop`, but
  `configuration_test.exs` still attempts to read and assert that deleted file.

## Goal

The supported local topology is:

```text
browser / host client
        |
        | https://app.localhost
        v
Tama Kit Caddy container
        |
        | private HTTP upstream
        v
host-native Memovee :4000

Memovee -> https://tama.app.localhost/.well-known/jwks.json -> Caddy -> Tama
```

Memovee must advertise and issue tokens from `https://app.localhost`, use
`https://tama.app.localhost/mcp/app` as the exact audience, and fetch Tama's
JWKS through the HTTPS public name. Docker routing names must remain private
transport details.

The runtime split is a required invariant:

| Service | Effective environment | Listener |
| --- | --- | --- |
| Memovee | host-native `MIX_ENV=dev` | private HTTP upstream reachable only for the managed Caddy path |
| Tama | official release image with `MIX_ENV=prod` | private HTTP inside Compose |
| Caddy | generated Compose service | public HTTPS for both `.localhost` names |

## Required changes

### MCP App configuration

Keep the current production validation rules. Do not permit non-loopback HTTP
or weaken same-origin validation. Do not change the standalone `dev` and `test`
defaults in a way that makes native development require Caddy and mkcert.

Add focused configured-environment tests proving that `dev` accepts the exact
generated HTTPS topology used by this integration. Retain production
regression coverage, but do not use it as a substitute for the real
`MIX_ENV=dev` path. HTTP `.localhost`, cross-origin JWKS, paths, queries, and
fragments remain rejected where required. The generated provider fragment,
not a new hard-coded application default, owns the active bootstrap values.

Remove the stale assertion against the deleted application-owned provider
contract. Memovee may validate its configuration roles and runtime behavior,
but must not duplicate or claim ownership of Tama Kit's generated local
contract.

### Phoenix listener and public URL

Add an explicit, validated local proxy mode or equivalent endpoint inputs that
separate:

- the public external origin (`https://app.localhost`);
- the private HTTP bind address and port used by Caddy; and
- the set of proxy addresses whose forwarding headers may be trusted.

Preserve the current loopback bind by default. Enabling Caddy reachability must
be explicit and limited to local development. Prefer binding only to the Docker
bridge address used by the generated Compose network. If the supported
cross-platform design requires `0.0.0.0`, require an explicit opt-in, warn that
the upstream port may be reachable from other interfaces, and add a runtime
preflight that rejects or clearly reports unintended exposure. Do not silently
broaden the listener merely because MCP App mode is configured.

Implement this in the development/runtime configuration path. Do not ask the
operator to run Memovee with `MIX_ENV=prod`, and do not move the production
database, secret-key-base, clustering, static-asset, or mailer requirements
into development. Likewise, do not enable the production compile-time
`force_ssl` profile merely to make Caddy work: Caddy owns TLS and Memovee's
upstream remains HTTP.

Configure the Phoenix external URL from one validated origin rather than
independent scheme, host, and port values that can drift. Relative browser
navigation and WebSocket connections must remain on the external HTTPS origin.
When the managed proxy mode is active, replace the blanket development
`check_origin: false` behavior with the exact generated HTTPS origin if
Phoenix supports doing so without breaking code reload; otherwise document and
test the narrowest safe development setting.

Do not derive the OAuth issuer from `Host`, `Forwarded`, or `X-Forwarded-*`.
Continue using `MEMOVEE_OAUTH_ISSUER` as the exact authority. Trust forwarded
client information only from the actual Caddy peer, never from arbitrary
callers or an entire private range without evidence.

### Generated environment loading

Update the repository loader contract to consume the Tama Kit-managed provider
fragment under `tama/`, preserving POSIX-shell compatibility and safe behavior
when the file is absent. The fragment remains private, ignored, untracked, and
the only generated owner of signing material.

The loader must make both OAuth values and the explicit proxy/listener inputs
available before Phoenix runtime configuration executes. It must not print or
copy secrets into another environment file.

### TLS trust for outbound Tama calls

The host must trust the mkcert root before Memovee fetches Tama's HTTPS JWKS.
First prove that the existing Req/TamaOAuth path honors the host trust store.
Do not add `verify_none` or a general TLS-skip flag. If explicit CA selection is
required on a supported platform, scope it to the Tama MCP App JWKS client,
accept only the public CA certificate, and preserve hostname verification.

## Verification

Cover at least:

- existing standalone development without Tama Kit or Caddy;
- configured HTTPS loading in the actual `MIX_ENV=dev` process, plus separate
  production regression coverage;
- default loopback binding and explicit Caddy-reachable binding;
- external URL, forwarded scheme, LiveView/WebSocket origin, and relative
  navigation through `https://app.localhost`;
- spoofed forwarding headers from an untrusted peer;
- OAuth metadata, JWKS, authorization, token, revocation, and introspection
  using the exact public issuer;
- successful hostname-verified HTTPS retrieval of Tama JWKS through Caddy;
- failure when the CA is untrusted, the certificate name is wrong, or Caddy is
  unavailable;
- provider fragment loading from the managed `tama/` path without secret
  disclosure; and
- the full lifecycle matrix in `disabled`, `prepared`, and `enabled` modes.

The cross-repository runtime gate must start Memovee in `prepared` with
`MIX_ENV=dev`, start the official Tama release with `MIX_ENV=prod`, prove
Caddy can reach both private upstreams, prove Tama reaches Memovee through
`https://app.localhost`, then complete the existing staged activation flow.
Passing against a production Memovee release or a development Tama process does
not satisfy this gate.

## Ownership and non-goals

- Memovee owns endpoint configuration, OAuth public identity, lifecycle,
  listener safety, and provider runtime tests.
- Tama Kit owns Caddy, mkcert orchestration, generated files, Docker aliases,
  topology planning, and bootstrap output.
- Tama owns `/mcp/app`, its introspection key, and protected-resource policy.
- Do not embed Caddy or certificate private keys in Memovee.
- Do not make native development depend on Tama Kit.
- Do not require Memovee to run in production for the local HTTPS topology.
- Do not rotate OAuth keys because the local public origin changes.
- Do not restore an application-owned copy of the Tama Kit local contract.

## Delivery coordination

Land the Memovee runtime support before advertising the local HTTPS bootstrap
as ready for Memovee. Pin the exact compatible Memovee and Tama revisions in
the Tama Kit runtime fixture, update the bundled `app-integration` guidance,
and require the three repositories' exact review heads to pass the
mixed-environment end-to-end gate before release.
